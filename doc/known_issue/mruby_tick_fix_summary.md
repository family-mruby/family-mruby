# mruby_tick_task クラッシュ修正 — やさしい解説サマリー

`task context corrupted: no proc on resume` クラッシュの原因と対処を、専門用語を
かみ砕いてまとめたもの。技術的な詳細は
[mruby_tick_task_investigation.md](mruby_tick_task_investigation.md) を参照。

（2026-06-05 時点。ESP32 実機で 30 分以上の連続稼働を確認済み。）

---

## 何が起きていたか

このシステムは複数の Ruby プログラム（カーネル、デスクトップ、各アプリ）を1台で同時に
動かしている。それらに公平に CPU を配るため、数ミリ秒ごとの「**心拍（tick）**」で
「そろそろ交代して」と促す仕組みがある。自分から譲らない（重い計算を回し続ける）
プログラムも、この心拍で**強制的に一時停止**させて他に順番を回す、という狙い。

問題は、この心拍が「**今すぐ止まれ**」という合図を**悪いタイミングで**出していたこと。
具体的には:

- あるプログラムが、画像描画などで **C言語の関数を呼び、その C 関数がさらに Ruby を
  呼び戻している最中**（＝処理が入れ子になっている状態）に、「止まれ」が効いてしまう。
- 画像描画は、子チップ（映像担当）へシリアル通信で依頼して返事を待つ処理で、
  **数ミリ秒〜数秒**かかる。この「入れ子で待っている間」に止められると、プログラム内部の
  **呼び出し履歴（どこまで処理したかの記録）**と**エラー処理の戻り先**が壊れた状態のまま
  放置される。
- しばらく後にその壊れた状態を使った瞬間に、`task context corrupted`（文脈が壊れた）／
  メモリ違反でクラッシュしていた。

### なぜ実機(ESP32)でだけ確実に出て、PC シミュレータで出なかったか

「危険な瞬間」の長さが違うから。実機はシリアル通信で**ミリ秒〜秒**と長く、危険な窓が
大きい。PC は内部通信が**マイクロ秒**で一瞬なので、まず当たらなかった。さらに PC 側の
テストで**マウス操作をしていなかった**ことも見逃しの原因（PC が安全という意味ではない）。

---

## 実施した対処

大きく2段階。

### 第1段（案D）：心拍の「実作業」を各プログラム自身に移した

以前は心拍が別スレッドから各プログラムの内部データ（タスク待ち行列）を直接いじっており、
これも競合の元だった。これをやめ、心拍は「印を付けるだけ」、実際の更新は**各プログラムが
自分のタイミングで**行うようにした。これで「別スレッドが同じデータを取り合う」競合は解消。

ただし、これだけではクラッシュは**直らなかった**（第2段が本丸）。

### 第2段（決め手）：「止まれ」を安全な場所でだけ効かせるようにした

- プログラムが「止まれ」の印を見ても、**入れ子の C 関数の中にいる間は止まらない**ように
  VM（Ruby 実行エンジン）を修正。C 関数から抜けて**自分の Ruby コードに戻った安全な瞬間
  まで、停止を自動的に先送り**する。
- あわせて、停止時に**失われていたエラー処理の戻り先を正しく復元**するようにした。

これにより「**自分から譲らない重いプログラムも強制停止できる**」という当初の要件は維持
したまま、内部状態の破壊だけを防げる。

## 検証結果

- ESP32 / PC(Linux) 両方ともビルドはクリーン（警告なし）。
- **ESP32 実機でデスクトップを操作し続けても（30 分以上）クラッシュ再発せず**。
- コミット（fmruby-core, `fix_tick_issue` ブランチ）:
  - `53d9e0d`（第1段）
  - `511e229`（第2段＝決め手）
  - 後続でデッドコード掃除のコミット

---

## 後片付け（トライ&エラーの残骸の削除）

第2段の修正で、旧式の「心拍ゲート」機構（C 関数中は心拍を配信しないためのフラグ群＝
`in_c_funcall` / `irq`）が不要になったため削除した。役目は VM 側の「安全な場所でだけ
止まる」判定に一本化された。

## 保守上の注意

決め手の修正のために VM 本体（`vm.c`、約3500行）を `lib/patch` に丸ごと取り込んでいる。
実変更は約20行だが、今後 picoruby 本体の `vm.c` が更新された場合は手動追従が必要。
