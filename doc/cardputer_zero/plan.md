# CardputerZero への移植 検討書

作成 2026-08-19 / 更新 2026-08-19 (5 章「描画の作り」を追加、P-1 段を新設)
状態: 検討のみ (未着手)

## 1. 要旨

M5Stack CardputerZero は名前こそ Cardputer 系だが、中身は **Raspberry Pi CM0 を
載せた小型 Linux 機**であり、ESP32 ではない。したがってこの移植は
「ESP-IDF の移植先が一つ増える」話ではなく、**既に完成している Linux 版
(rake build:linux の 3 プロセス構成) を aarch64 の実機で動かす**話になる。

調査の結論は次のとおり。

- **表示・入力・音の受け皿は、今 headless 検証で毎日動かしているものがそのまま乗る**。
  実機には SDL2 が apt で入り、sdl2-display には software 描画への切り替えも
  既に入っているので、描画装置の有無どちらに転んでも起動はする。
- **描画装置 (GPU) があるかどうかが未確認で、HDMI 出力の作りはこれで正反対になる**。
  当初「GPU 無し」と書いたが、調査結果のなかに逆を示す証拠がある (5.1)。
- **最大の未確認点は「ESP-IDF の linux ターゲットが aarch64 で通るか」の一点**。
  IDF 側にも自前コードにも CPU 依存の記述が見つからなかったので見込みは高いが、
  実際にビルドを通すまでは断定しない。
- ビルド機は **Jetson Orin NX (aarch64 実機)** を使う。qemu 経由の遅さを避けられる上、
  Jetson 自身が aarch64 Linux なので、**実機に触る前に Jetson 上で全体を動かして
  切り分けられる**。
- 実装上の作業量は「移植」というより**配線**に近い。ただし画面が 320x170 で
  縦が 70px 足りない点だけは、画面の作りに正面から効く。

## 2. 対象機の事実

CardputerZero/AppBuilder と CardputerZero/Template の 2 リポジトリを読んで確認した
範囲。カタログ値ではなく、**ビルドと配布の仕組みから読み取れた実運用の姿**を記す。

### 2.1 ハードウェア

| 項目 | 値 |
|---|---|
| SoC | Raspberry Pi CM0 (BCM2710A1 / RP3A0, Cortex-A53 4コア 1GHz) |
| RAM | 512MB LPDDR2 |
| 記憶 | microSD |
| 内蔵画面 | 1.9型 320x170 RGB565、`/dev/fb0` |
| 外部出力 | HDMI (1080p30) |
| 入力 | 46 キーのマトリクス。**evdev として `/dev/input/event*` に出る** |
| 音 | スピーカー + マイク、ALSA |
| GPU | **要確認**。VideoCore IV が使える見込みが高い (5.1) |

内蔵 RAM の枯渇と戦ってきた S3 (8MB PSRAM) や P4 と比べれば桁違いに楽になり、
CPU も 240MHz の Xtensa から 1GHz の A53 4 コアになる。ただし 512MB に labwc と
3 プロセスが同居するので、**「資源制約が消える」ではなく「実測して余裕を確認する」**
に留める (7 の 7)。

### 2.2 ソフトウェア環境 (ここが移植の可否を決めた)

- Debian 系の Linux が動き、`libsdl2-2.0-0` をはじめ通常の deb パッケージが使える。
  用意されている作例も C/LVGL・SDL2・Qt・Python・Rust・NES エミュレータと雑多で、
  **中身が何であるかは問われない**。
- **常時 labwc (Wayland の画面合成) が `/dev/dri/card0` を握っている**。
  このため SDL2 の KMSDRM 経路は画面を取れず、**wayland 経路が本命**。
  作例の起動 script も wayland → kmsdrm → offscreen の順に試す作りになっている。
- 一般利用者は `pi` (uid 1000)。アプリは APPLaunch という一覧から起動され、
  `/dev/dri` `/dev/fb0` `/dev/input/event*` に触るには video/render/input の
  グループに入っている必要がある。
- 配布形式は **`.deb`**。`.desktop` を APPLaunch の場所に置き、必要なら systemd の
  サービスも入れる。アイコンは共有の場所に入るので**名前の衝突に注意**と
  Template に明記がある。
- 交差ビルドは、BSP の sysroot を落として `aarch64-linux-gnu-gcc` で通す方式と、
  **arm64 の Ubuntu 24.04 コンテナで素直に native ビルドする方式**の両方が用意されている。

## 3. Family mruby 側の適合性

移植の山になりそうな箇所を先に潰した。以下は実際に確認した結果。

### 3.1 ESP-IDF の linux ターゲットに CPU 依存が無いこと

IDF v5.5.4 の FreeRTOS Linux 移植 (`components/freertos/FreeRTOS-Kernel/portable/linux/`)
は `port.c` / `port_idf.c` / `utils/wait_for_event.c` の 3 本だけで、
**x86 前提の記述も ucontext も無い。pthread と signal しか使っていない**。
これは「aarch64 でも素直に通る」ことを強く示唆する。

### 3.2 自前コードに CPU 依存が無いこと

- fmruby-core / fmruby-graphics-audio の自前コードに `__x86_64__` 依存は無い。
  検出されたのは msgpack が持ち込む移植性判定ヘッダのみで、これは正しく動く側。
- graphics-audio の TLSF だけが 32/64bit を自前で判定しているが、`__LP64__` を
  見ているので **aarch64 でも正しく 64bit 側に落ちる**。ここは黙って壊れうる箇所
  だったので個別に確認した。
- 語順 (エンディアン) は同じ。

### 3.3 表示側がそのまま使えること

`fmruby-graphics-audio/sdl2-display/main.c` は **1 枚の C ファイルと SDL2 だけ**で、
外部依存が無い。しかも accelerated な描画器が取れなければ software 描画に落ちる
分岐が既に入っている (headless 検証のために入れたものが、描画装置が無かった場合の
保険にそのままなる)。表示の大きさは共有メモリのヘッダから読むので、解像度も設定で追従する。
描画の費用と、SDL2 を外すかどうかの判断は 5 章に分けて書いた。

### 3.4 現状の構成 (移す対象)

3 プロセスが共有メモリと Unix ソケットで繋がっている。

```
fmruby-core.elf ──┐                        POSIX 共有メモリ /fmrb_display
                  ├─ /var/run/fmrb/*.sock ─ (RGB332 二重緩衝)
fmruby-graphics-audio.elf ─┤                        │
                           └── sdl2-display ────────┘ ← SDL2 で表示・音・入力
```

固定で書かれている場所は次のとおり。**実機ではこれらを可変にする必要がある**。

| 種別 | 現在の値 | 定義位置 |
|---|---|---|
| 共有メモリ名 | `/fmrb_display` | graphics-audio `main/common/shm_display.h` |
| 入力ソケット | `/var/run/fmrb/fmrb_sdl_input` | 同上 |
| 注入ソケット | `/var/run/fmrb/fmrb_inject` | 同上 |
| USB 入力ソケット | `/var/run/fmrb/fmrb_input_socket` | core `main/drivers/usb/usb_task_linux.c`、graphics-audio `main/input_linux/input_socket.c` |
| 連絡ソケット | `/var/run/fmrb/fmrb_socket` | graphics-audio `main/communication/comm_socket_server.c` |
| ファイル置き場 | 作業ディレクトリ相対の `flash/` | graphics-audio `main/file_transfer/file_transfer_handler.c` |

`flash/` が作業ディレクトリ相対である点は配布時に効く。**書き込み可能な場所に
flash/ を置き、そこへ移動してから起動する**必要がある。

## 4. 方式の選択

| 案 | 内容 | 判定 |
|---|---|---|
| **A. Linux 版をそのまま aarch64 で動かす** | 3 プロセス構成を維持し、sdl2-display を実機の画面・入力・音に繋ぐ | **採用**。作業が配線に収まる |
| B. ESP-IDF を捨てて素の Linux アプリに書き直す | FreeRTOS 依存を POSIX に置換 | 却下。FreeRTOS の API 依存が広範で、実機 2 機種と別物の第 3 の実装を抱えることになる |
| C. 3 プロセスを 1 プロセスに畳む | 起動と後始末が簡単になる | 将来検討。SIGALRM の衝突を避けるために分けた経緯があるので、今やる理由が無い |

## 5. 描画の作り (SDL2 を外すか、OpenGL を使うか)

「将来は SDL2 依存を外し、OpenGL を使って描画を最適化したい」という方針について、
今の経路の費用を数えた。**結論は「実機に描画装置があるかどうかで答えが正反対に
なる」**なので、まずそこを確かめる。

### 5.1 描画装置の有無 (最優先の未確認事項)

2.1 に当初「GPU 無し。Mesa の software 描画のみ」と書いたが、**これは誤りの
可能性が高い**。同じ調査結果のなかに、逆を示す証拠が 2 つある。

- **labwc が `/dev/dri/card0` を握っている** (2.2)。描画装置が無ければ、ここに出るのは
  素の面だけで、画面合成に使う形にはなりにくい。
- **`render` グループが要る**と書かれている (2.2)。この group は
  `/dev/dri/renderD128`、つまり 3D 演算の入口のためのもので、
  描画装置が無ければ存在する理由がない。

加えて CM0 の SoC (BCM2710A1 / RP3A0) は Pi Zero 2 W と同じ系統で、
**VideoCore IV を積んでおり OpenGL ES 2.0 が使える**。「software 描画のみ」は、
作例の起動 script が offscreen まで落ちる分岐を持っていたのを見ての推測であり、
裏は取れていない。

実機で次を見れば決まる。

```
ls /dev/dri/            # renderD128 があるか
eglinfo | head          # または wlr-randr / glxinfo -B
```

### 5.2 今の経路が 1 枚ごとにやっていること

`fmruby-graphics-audio/sdl2-display/main.c` の `render_frame` は 3 つを行っている。

1. 320x240 = 76,800 画素を 1 画素ずつ表引きして **RGB24 に展開** (8bit の書き込みを
   3 回、計 230KB)
2. `SDL_RenderCopy` で窓の大きさへ**拡大**
3. **毎回全面を送る**。共有メモリの構造体 (`main/common/shm_display.h`) は
   書き込み番号しか持たず、**どこが変わったかの情報が無い**

重いのは 2 の拡大で、描画装置が無ければこれが全部 CPU に乗る。

### 5.3 内蔵画面 (320x170) では、そもそも拡大が要らない

内蔵画面は 320 幅で、こちらの画面も 320 幅。倍率を 1 にすれば拡大が消え、残るのは
54,400 画素の色形式の変換だけになる。RGB332 から RGB565 なら 256 語の表を引いて
16bit を 1 回書くだけで、A53 なら 1 枚あたり数十マイクロ秒。**内蔵画面については
これで最適化の話がほぼ終わる。** OpenGL は要らない。

### 5.4 HDMI (ここで描画装置の有無が効く)

320x240 を 1920x1080 へ引き伸ばすと、出力側は 2,073,600 画素 x 4 バイト =
**1 枚 8.3MB**。30 回/秒で **毎秒 249MB の書き込み**になり、labwc がその後もう一度
全面を写すならさらに倍。LPDDR2 の帯域からすると、これだけで機械が鈍くなる。

**描画装置がある場合** — 拡大は既に加速されている。ここは誤解しやすいので明記する。
`SDL_CreateRenderer(..., SDL_RENDERER_ACCELERATED)` は v3d が使えるなら GLES2 の
実装を選ぶので、**`SDL_RenderCopy` の拡大は今でも描画装置側で行われている**。
つまり「HDMI のために SDL2 を外す」は、拡大を理由にする限り成立しない。

手書きにして初めて得られるのは**送り込む量**のほうで、これは実際に効く。
RGB332 の 8bit の面をそのまま渡し、256 色の色表をもう 1 枚の面として渡して、
断片処理 (fragment shader) の中で引く形にすると:

| | CPU の変換処理 | 1 枚あたりの転送量 |
|---|---|---|
| 今 (RGB24 に展開して渡す) | 76,800 画素の表引き x 3 バイト書き | 230KB |
| 色表を断片処理側に置く | **無し** (共有メモリからそのまま渡す) | **77KB** |

**RGB332 であることがここでは利点になる**。1 画素 1 バイトなので送る量が 1/3 になり、
`render_frame` の変換処理が丸ごと消える。1GHz の A53 で毎秒 60 回まわす処理が一つ
消えるのは効く。**これが「HDMI のために OpenGL」の正しい形**であり、狙いは拡大の
肩代わりではなく、変換処理の消滅と転送量の削減。

**描画装置が無い場合** — OpenGL を使ってはいけない。llvmpipe (CPU で塗る実装) が
動くだけで、全画面 1 枚を貼る用途では手書きの変換より速くならず、常駐分だけ
512MB を圧迫する。この場合の答えは **HDMI 側の解像度を下げること**。640x480 で
出せば整数 2 倍で 1 枚 1.2MB に収まり、拡大は表示装置がタダで行う。整数倍のほうが
絵も濁らない。**320 幅の画面を 1080p に引き伸ばす必然性は元々無い。**

### 5.5 SDL2 を外す本当の理由は、描画ではなく入力

SDL2 は描画・入力・音の 3 つを担っている。外すなら 3 つとも書くことになるので、
別々に採算を見る。

| 仕事 | 外す価値 |
|---|---|
| 描画 | **低い**。5.2 の 1〜3 の改善は SDL2 のままでもできる。送出先を選ぶ段になって初めて要る |
| 入力 | **高い** (下記) |
| 音 | 中くらい。ALSA を直接叩くのは 150 行程度で、遅延を自分で決められる |

入力の価値が高いのは、CLAUDE.md に書いてある**半角/全角とカタカナのキーが X11 を
通ると壊れる**問題が、まさに「表示系を経由するせいで生の押下が取れない」ことに
由来するため。CardputerZero は evdev から生のキー符号が出る機械なので、
**`/dev/input/event*` を直接読めばこの層を丸ごと消せる**。46 キーの Fn 併用の
割り当ても、自分で表を持つほうが素直になる。

### 5.6 段取り

この境界はもともと綺麗に引けている。表示処理は共有メモリと Unix ソケットの向こう側に
ある独立した 520 行の 1 プロセスで、本体はそれが何であるかを知らない。だから
「SDL2 を外す」は書き換えではなく、**同じ約束を守る別の実行ファイルを 1 本足す**話に
できる。母艦側を SDL2 のまま残せるので、毎日の headless 検証・入力注入・画面撮影の
道具立てはそのまま生き残る。

```
core / graphics-audio ──共有メモリ + ソケット──┬─ sdl2-display   (母艦。今のまま)
                                               └─ fbdev-display (実機。新規)
```

着手の順序は次のとおり。

1. **まず計る**。`render_frame` を変換と送出に分けて時間を出す。今この数字が無いため、
   最適化の議論が全部推測になっている。sim で今日できる。
2. **共有メモリに変更範囲を持たせる** (5.2 の 3)。graphics-audio は範囲単位の描画に
   作り替え済みで変更範囲を知っているのに、共有メモリの境で捨てている。
   **これは描画装置の有無に関わらず効き、OpenGL なら転送も部分更新にできる**ので、
   分かれ道を待たずに進められる。
3. 実機で**倍率 1 + 画面の形式へ直接変換**にする。内蔵画面はここで終わるはず。
4. それでも足りなければ、送出先を選んで別プロセスを書く
   (`/dev/fb0` 直書き / wl_shm / EGL+GLES2)。入力の evdev 直読みも一緒にやる。

## 6. 段階計画

各段階に**完了条件**を書く。前段が終わるまで次に進まない。

### P-1: 実機を 5 分だけ触る (最優先)

**器の作り方も描画の方式も、実機を一度見ないと決まらない。** Jetson で器を組む前に
ここを済ませる。当初 P1 に置いていたが、それでは決定の順序が逆になる。

```
ldd --version; cat /etc/os-release   # 器の元 (7 の 1)
ls /dev/dri/                         # 描画装置の有無 (5.1、7 の 2)
ls /dev/input/by-path/               # キーの出方 (7 の 6)
free -m                              # 空きメモリ (7 の 7)
```

**完了条件**: 上の 4 つの答えが記録されていること。

### P0: Jetson Orin NX で aarch64 ビルドを通す (実機不要)

ここが全体の可否を決める。

1. ビルド用の器を用意する。現行の `ghcr.io/family-mruby/fmruby-esp32-build:v5.5.4`
   は **amd64 のみ**で、その Dockerfile はこの 2 リポジトリには無い (別管理)。
   arm64 の Ubuntu に IDF v5.5.4 を入れただけの軽い器を新たに作るのが早い。
   **ESP-IDF は aarch64 の Linux を正式に対応している** (確認結果は 6.1)。
2. `rake build:linux` を core と graphics-audio の両方で通す。
3. sdl2-display を Jetson 上でそのままビルドする。

**完了条件**: `file build/fmruby-core.elf` と `.../fmruby-graphics-audio.elf` が
いずれも **aarch64** と出ること。ここで x86-64 と出ていたら偽の成功なので、
必ず確認する (esp32 の残骸で Xtensa の偽グリーンが出た前例がある)。

#### 6.1 ESP-IDF の aarch64 対応 (確認済み)

「ESP-IDF が arm の Linux に入るか」は移植の前提なので先に確かめた。**入る**。

- `tools/idf_tools.py` は `Linux-aarch64` / `Linux-arm64` を **`linux-arm64` という
  正式な対象として表に持っている**。amd64 と同格の扱いで、特別な回避は要らない。
- `tools/tools.json` を見ると、既定で入る道具 (xtensa-esp-elf、riscv32-esp-elf、
  各 gdb、esp32ulp-elf、openocd-esp32) は **すべて linux-arm64 の実体を持つ**。
  `esp-rom-elfs` は CPU に依らない `any`。
- 例外は `ninja` で、これは linux 向けの実体を IDF が配っていない
  (macOS と Windows のみ)。Linux では OS の側から入れる前提なので、
  `apt install ninja-build` で足りる。`cmake` は linux-arm64 の実体がある。
- そもそも **今回の用途では ESP の道具立ては一つも要らない**。
  linux ターゲットの `tools/cmake/toolchain-linux.cmake` は
  「host ビルドには不要なので置いてあるだけ」と書かれた**空の置き石**であり、
  **ホストの gcc がそのまま使われる**。必要なのは python 環境と cmake / ninja と
  ホストの gcc だけ。

したがって器は「arm64 の Ubuntu + IDF v5.5.4 (最小)」で組める。

注意: `idf_tools.py` 自身が警告しているとおり、**arm64 の機械の上で armhf の
入れ物を使うと 32bit 側として誤検出される**。Jetson で器を作るときは
必ず arm64 の元を使う。

なお Jetson の JetPack 6 は Ubuntu 22.04 (Python 3.10) で、IDF v5.5 の要件を満たす。

### P0.5: Jetson 上で全体を動かす (実機不要)

Jetson は aarch64 の Linux なので、**実機に触る前に 3 プロセスをそのまま起動できる**。
ここで CPU 依存の不具合を切り分けておく。

ついでに **`SDL_RENDER_DRIVER=software` を強制して 1 枚あたりの時間を測る** (5.6 の 1)。
Jetson には描画装置があり A53 より速いので、この値は下限にしかならないが、
**ここで既に間に合っていなければ実機では確実に間に合わない**ことは分かる。

**完了条件**: Jetson の画面に起動画面が出て、キー入力が通り、
`tools/fmrb_screenshot.py` で画面が撮れること。

注意: ここで確定するのは「aarch64 で動く」ことだけで、**実機固有の危険は一つも
潰れない**。Jetson には描画装置があり画面合成も labwc ではないので、labwc 下での
全画面 (7 の 4)、描画装置なしの描画速度、evdev の 46 キー、512MB はそのまま残る。

### P1: 実機で動かす (最小構成)

1. 実機へ 3 本の実行ファイルと `flash/` を持ち込み、手で起動する。
2. `SDL_VIDEODRIVER=wayland`、`SDL_AUDIODRIVER=alsa`。
3. ソケットの置き場所を可変にする (環境変数、既定は現行の `/var/run/fmrb`)。
   実機では `/run/user/1000` 配下が素直。
4. 解像度は当面 320x240 のままとし、はみ出しは許容する。

**完了条件**: 内蔵画面に起動画面が出て、内蔵キーボードで desktop を操作できること。

### P2: 実機に合わせる

- **画面 320x170 の設定を追加**する。設定に幅と高さがあるので値を通すこと自体は容易。
  ただし desktop とアプリは 240 行を前提にしているので、**縦 70px の不足は
  画面の作りに正面から効く**。HDMI があるので、内蔵は 320x170 の簡易表示、
  外部は Modern と同じ 426x240、という二段構えが現実的。
  (解像度は graphics-audio が `flash/etc/display_conf_linux.txt` に覚えており
  変更は次回起動から効く点に注意)
- **倍率を 1 にして拡大を消す**。内蔵画面はこれで描画の費用がほぼ無くなる (5.3)。
  HDMI 側の作りは描画装置の有無で分かれる (5.4)。
- **46 キーの対応表**。evdev から SDL 経由で来るので既存の経路に乗るが、
  Fn 併用の割り当てと、Ctrl/Esc など常用キーの出方を実測して決める。
- 音を ALSA で鳴らす。

**完了条件**: 内蔵画面だけで editor を開いてアプリを書き、実行できること。

### P3: 配布物にする

- `.deb` 化。**3 プロセス構成なので実行ファイル 1 本ではなく起動 script でまとめる**。
  作例にも同じ形 (script を `/usr/share/APPLaunch/bin/` に置く) があるので、それに倣う。
- 終了時に 3 本まとめて片付ける (プロセス群への signal)。
- `flash/` は共有の場所に入れ、初回起動時に利用者の書き込み可能な場所へ複製してから
  そこへ移動する。
- アイコンとパッケージ名の衝突に注意する。

**完了条件**: 実機に `.deb` を入れ、APPLaunch の一覧から起動・終了できること。

## 7. 未確定事項

**確かめるまで断定しない**もの。上ほど重要。

1. **実機の Linux 配布版と glibc の版**。作業の器をこれに合わせる必要がある。
   AppBuilder が公式に用意している器は arm64 の Ubuntu 24.04 (glibc 2.39) だが、
   起動 script に出てくる `pi` という利用者名と labwc という組み合わせは
   Raspberry Pi OS (glibc 2.36) を思わせる。**両者は両立しない**。
   新しい glibc で作ったものは古い glibc の機械では動かないので、ここを取り違えると
   実機で起動すらしない。**実機で `ldd --version` を見るのが唯一の確実な確認**。
   Jetson (JetPack 6 は Ubuntu 22.04 = glibc 2.35) を素で使う場合は、
   むしろ古い側で作ることになるので安全側に倒れる。
2. **実機に描画装置があるか** (P-1 で判明)。**HDMI 出力の作りが正反対になる**ので、
   ここが決まらないと 5 章の分岐が閉じない。あれば拡大は加速され (SDL2 のままでも
   効く)、手書きに進む利益は転送量の削減になる。無ければ OpenGL は使わず、
   HDMI 側の解像度を下げる。証拠は 5.1 のとおりあると見ているが未確認。
3. **IDF の linux ターゲットが aarch64 で通るか** (P0 で判明)。
   IDF が aarch64 のホストに入ること自体は確認済み (6.1)。残る未確認は
   「linux ターゲットとして組んだ成果物が aarch64 で正しく動くか」。
   IDF はこの構成を「ホスト＝ターゲット」の試験用途として提供しており、
   aarch64 ホストは主用途ではない。3.1 の調査から見込みは高いが未確認。
4. **画面合成が動いている状態で窓を全画面にできるか**。labwc が出力を握っているので、
   窓の扱いは画面合成側の裁量。`/dev/fb0` へ直書きする案も、labwc と競合しないか
   ここで決まる。
5. **HDMI と内蔵画面の同時利用**と、それぞれに別の解像度を出せるか。
6. **46 キーが標準的なキー符号で出るか**、Fn の扱い。
7. **512MB で足りるか** (P-1 で目安、P1 で実測)。2.1 に「資源制約の話は消える」と
   書いたが、これは言い過ぎ。labwc と 3 プロセスが同居し、graphics-audio は
   共有メモリの二重緩衝と TLSF の池を起動時に確保する側なので、**実測して余裕を
   確認する**に留める。
8. APPLaunch がアプリを終了させる方法 (signal の種類、3 プロセスの後始末)。

## 8. 位置づけ

技術的に可能であることと、やる意味があることは別なので分けて書く。

Family mruby の主題は「電源を入れたら Ruby」「限られた資源の中で作る」ことにある。
Linux の上で動かすと、**持ち運べる検証環境が 1 台増える**という位置づけになり、
Retro / Modern と同列の第 3 の機種にはならない。一方で、Modern を
「作る機械」と定めて HDMI 出力まで見ている方針とは噛み合う。
**母艦なしで編集・実行できる Ruby 機**としての価値は独立して存在する。

また、CM0 は S3 と桁違いに速いので、**Spinel AOT を使う理由がこの機械では薄い**。
linux 版は mruby 構成のままでも快適に動くはずである。

これは「Spinel が標準」という現行方針と**矛盾しない**、と整理できる。engine policy は
「Spinel が標準・mruby は互換検証」であり、**検証構成は標準と全 mruby の 2 点**と
決めている。CM0 が mruby 構成を常用で回す機械になるなら、**2 点目の検証構成が
毎日実機で動く**ことになり、今いちばん弱い側 (mruby 構成が置いていかれること) を
むしろ補う。

判断の分かれ目は「Retro/Modern の隣に並べる 3 番目のハードとして出すのか、
自分用の携帯開発機として作るのか」であり、これは技術の問題ではない。

**ただし、この判断が決まらないと P2 が書けない。** 320x170 の扱いが答えそのもので、

- **3 番目の機種**にするなら、desktop とアプリを 170 行でも成立するように作り直す
  話になる。CardputerZero だけの作業では終わらず、全機種の画面の作りに手が入る。
- **携帯開発機**なら、外部出力を常用の前提にして、内蔵画面は起動確認と簡易表示だけで
  済む。P2 の「二段構え」が素直に落ちる。

先に後者と決めてしまえば、P2 は「320x170 の設定を足してはみ出しを許容する」で
終わる。**未決のまま P2 に入らない。**
