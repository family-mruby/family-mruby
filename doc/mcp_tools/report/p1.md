# fmrb-mcp P1 実装報告

実装: 2026-08-28。計画は `doc/mcp_tools/p1_plan.md` (書き換えていない)。
本書は実装中に判明した計画との差分と、確定した結論を残すためのもの。

## 成果物

```
tools/mcp/fmrb_mcp_server.rb   # MCP stdio サーバ (ツール 4 つ)
tools/mcp/lib/serial_manager.rb # capture 子プロセスの所有・flock・flash 連携
tools/mcp/selftest.rb          # 実機なしの確認 (32 項目)
tools/mcp/README.md
.mcp.json                      # リポジトリ直下
```

環境: mcp gem 1.4.0 / ruby 3.2.6。`MCP::Tool.define` + `MCP::Server` +
`MCP::Server::Transports::StdioTransport` で足りた。SDK 側に困った点は無い。
`.mcp.json` は `command: ruby` / `args: ["tools/mcp/fmrb_mcp_server.rb"]`。

## 計画との差分 (実装して分かったこと)

### 1. `-t 0` は「無限」ではなく「何も採らない」

`fmrb_serial_capture.py` は `end = time.time() + secs` の while ループなので、
`-t 0` は即終了する。開きっぱなし運用は計画どおり大きな値 (86400 = 24 時間)
を渡すのが正解。24 時間で勝手に終わることは serial_start の description に
書いた。

### 2. capture は出力ファイルを切り詰める (計画の「追記」は誤り)

`open(args.out, "wb")` なので、capture を起動するたびに出力ファイルは空に
なる。計画は capture.log 1 本を想定していたが、それだと **flash のたびに
直前までのログが消える** (flash は停止 → 再開なので必ず踏む)。

区間を分けて解決した。

- `current.log` — 稼働中の capture が書いている区間
- `capture.log` — 終了した区間を追記したもの (capture 停止時に current を
  ここへ移す)
- `serial_log` は両方を繋いで読む。flash 後のブート要約は `current.log`
  だけを見る (直前の区間を混ぜない)。

### 3. grep は既定で固定文字列、`regex: true` で正規表現

計画は「固定文字列。正規表現にするなら例外を握って明示エラー」。両方入れた
が、既定は固定文字列にした。理由は無言の穴があるため: CLAUDE.md 由来の
`Guru\|abort` (シェルの grep BRE) を Ruby の Regexp として解釈すると
リテラル `Guru|abort` を探すことになり、**エラーも出ずに 0 件**を返す。
description に「`Guru|abort` と書く、`Guru\|abort` ではない」と明記した。

### 4. ブートバナーが無いことを失敗と呼ばない

flash 後の再開は `--no-reset` なので、**ブートがすでに流れ切った後に
attach することがある**。バナーが無い = 起動していない、ではない。
要約はこれを区別して「バナーから採りたければ serial_start(reset: true)」と
案内する。DL モード滞留 (`waiting for download` / `boot:0x…(DOWNLOAD`) も
「ブートループではない、ボタンリセットを依頼」と名指しで返す (計画どおり)。

### 5. capture が動いていなければ flash 後も起動しない

計画には無かった分岐。動いていなかったものを勝手に開くとボードにリセットが
かかる (= 黙って状態を変える) ので、起動せず「ブートログは無い。見たければ
先に serial_start」と返す。

### 6. serial_stop も孤児を始末する

計画はサーバ終了時の後始末だけを求めていたが、**前のサーバが死んだ後に
残った capture** をユーザが片付ける先は serial_stop が自然。
`capture.meta.json` に記録されたポートのロックが取れたときだけ、pid と
`/proc/<pid>/cmdline` を確かめて始末する (ハードウェアの探索はしない)。

### 7. ログのバイト列は素通しできない

シリアルは生バイト。書き込み途中を読むので UTF-8 が途中で切れることがあり、
そのまま JSON にすると落ちる。ESP-IDF の色付けエスケープも混ざる。
`scrub` + ANSI 除去 + CRLF 正規化を通してから返している。

### 8. ポートが見つからないときは usbipd を案内する

`rake check-port` が「No serial devices found」で落ちたとき、WSL では
`rake attach` 待ちである可能性が高い。サーバからは実行しない (Windows 側の
権限) ので、エラー文でユーザに依頼するよう書いた。

### 9. `rake flash` はポートを自前で決める

capture のポートを引数で明示した場合、`rake flash` が使う
`fmruby-core/.serial_port` と食い違いうる (rake タスクはキャッシュしか見ない)。
食い違ったら黙って進まず、どちらを焼くのかを notes に出す。

## selftest (実機なしで通る、32 項目)

計画の 4 項目に加えて、**実機がなくても通せる経路は全部通した**。
socat の pty ペアを仮想シリアルポートにすると、capture の実経路
(python 起動 → 採取 → ファイル → serial_log) がハードウェア無しで動く。

1. initialize / tools/list (4 ツール、description あり)
2. capture もログも無い状態の serial_log、無効な正規表現の明示エラー
3. flock 衝突 → 「他セッションが使用中」 (子プロセスを起動していないことも確認)
4. 仮想ポートでの実採取: 起動 / 二重起動が no-op / 到着したバイトが読める /
   grep / 停止 / **停止と再起動をまたいでも前の区間が残る** (差分 2 の回帰)
5. **サーバに SIGTERM → capture の孤児が残らない** (計画の受け入れ 5 が
   実機なしで確認できた)
6. stdout が JSON-RPC だけ
7. ブートログの読み (DL 滞留を誤診しない / crash 行の計数 / 健全 / 無音) と
   子プロセス実行 (成功・失敗・タイムアウト・コマンド不在)

`rake check-port` の実経路も手で 1 回通した (ボード未接続 → 明示エラー +
usbipd の案内)。

## 実機受け入れ (2026-08-28〜29, Tab5 / ESP32-P4 / /dev/ttyACM0)

p1_plan.md 5 章の 4 項目すべてを実機で確認した。**全部合格**。

- **1. `serial_start(reset: true)` でブートから採れる — 合格**。リセットが
  かかり、`I (417) esp_image: segment 1` (二次ブートローダ) から
  `boot: Family mruby OS version 2.1.0`、M1| スナップショット 24 本、
  511 行まで通しで採れた。
- **2. `serial_log` を 5 回連続で呼んでもリセットが起きない — 合格**。
  リセット原因行は 0 のまま、`total_lines` は 486→511 と増え続けた
  (= ボードは動いたまま、capture も生きたまま読めている)。
- **3. capture 稼働中の flash — 合格**。人手ゼロで 66.3 秒。退避 → 書き込み
  (`Wrote 8388608 bytes ... Hash of data verified`) → `--no-reset` 再開 →
  要約まで通った。capture は別 pid (2622385 → 2623129) で自動的に復帰し、
  要約は「healthy: no crash markers, firmware reached its boot
  instrumentation」、crash 0 / DL 滞留なし。直後の `serial_log` で WiFi 接続と
  remote desktop の起動まで見えている。flash 中は capture プロセスが 0 本に
  なり (ポートを明け渡している)、`current.log` が `capture.log` に畳まれる
  ことも実地で確認した。
- **4. 2 セッション目の `serial_start` が明示エラー — 合格**。
  「`/dev/ttyACM0` is in use by another session (server pid …)」を返し、
  1 本目の capture は無傷で継続した。

### Tab5 はポートを開くだけでリブートする (最初の見立ては逆だった)

item 1 の直後、「Tab5 は ROM バナーを採れない」と結論しかけたが**誤り**
だった。flash 後のログにバナーが出たので切り分け直したところ、両方の経路で
再現した。

| `reset:` | Tab5 で起きること | ログの始まり |
|---|---|---|
| `false` (`--no-reset`) | **リブートする** (`rst:0x17 (CHIP_USB_UART_RESET)`) | ROM バナーから |
| `true` | **2 回リブートする** (open で 1 回、RTS パルスで 1 回) | 二次ブートローダから (最初の約 0.4 秒が USB 再列挙に食われる) |

つまり Tab5 では、

- `reset: false` は「触らずに横から覗く」ではない。**開いた時点で 1 回落ちる**。
  USB-Serial-JTAG がチップ内蔵で、ホストの DTR/RTS がそのままチップリセットに
  なるため。`--no-reset` でも避けられない (fmrb_serial_capture.py の
  docstring が「アダプタによっては open だけでリセットがかかる」と断っている
  とおりの挙動)。
- **`reset: false` の方が良いログが採れる** (バナーから)。`reset: true` は
  2 回目のリセットでバナーを失うので、この機種では損。S3 (別バスの
  USB-UART ブリッジ) とは逆になる。

serial_start の description をこの実測に書き換えた。**「開くのは 1 回きり、
あとはファイルを読む」という設計の値打ちは Tab5 でむしろ上がる**: 覗くたびに
開き直す運用なら毎回ボードが落ちる。

`boot_summary` が「起動したか」を ROM バナーだけで見ていた点は直した
(`esp_image: segment` / `boot: Loaded app from partition` / `cpu_start:` を
起動の印に加え、ROM バナーと二次ブートローダを区別して返す)。reset: true の
Tab5 ログを健全と読めるようになった。selftest にもその形を 1 項目足した
(計 32 項目)。

### flash のタイムアウトを 5 分 → 15 分にした

書き込み途中で kill するとアプリ区画が半端に書かれる。タイムアウトは
「中断する手段」ではなく「刺さったときの最後の砦」なので、実際の書き込み
(実測 66 秒、idf.py のビルド確認込み) より十分上に置く。

### サーバ終了時の current.log

capture 停止だけでは `current.log` は残る (次の `serial_start` が
`capture.log` へ畳む)。読む側は `serial_log` が両方を繋ぐので影響しないが、
正常終了 (at_exit) では畳んでから終わるようにした。シグナル trap では
ファイル操作を増やさない。
