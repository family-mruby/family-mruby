## 計画との差分 (実装して分かったこと)

### 1. 既存 CLI の `abort` はサーバでは自殺になる

`tools/fmrb_rd_http.rb` は到達不能や無応答を `abort` で報告する (CLI として
は正しい)。これをサーバ内でそのまま呼ぶと **SystemExit がサーバ本体を殺す**。
CLI を書き換えず、`rescue SystemExit` で `Tab5Unreachable` に変換して受けて
いる。同じ HTTP クライアントを共有し続けたいので、fork するよりこちらを選んだ。

### 2. 偽 Tab5 は名前空間の中でしか立てられない

エンドポイントは **port 80 固定** (rd_http、および CLI 3 本が直書き)。
非特権プロセスは 80 を bind できないので、素直には偽サーバを立てられない。
`unshare -rn` (ユーザ + ネットワーク名前空間) の中なら 127.0.0.1:80 は
自分のものになり、**サーバも rd_* CLI も無改造のまま実経路を通せる**。
selftest はこの中で `selftest_tab5.rb` を走らせ、名前空間が使えない環境では
SKIPPED にする。CLI に「ポート指定」を足す (= 改変) 案は採らなかった。

### 3. `/status` は解決時だけでなく毎回引く

計画は「解決したら `/status` で確かめてキャッシュ」。実装では**呼び出しの
たびに引く**ことにした。LAN の小さな GET 1 本で、

- 全ツールの失敗が 1 か所 (resolve) に集まる
- キャッシュが古くなった瞬間に気づける (操作を始めてから気づくと、途中まで
  やった転送などの後始末が要る)

という利点が、往復 1 回分のコストに見合う。キャッシュが応答しなければ
捨てて 1 回だけ引き直す (計画どおり)。

### 4. 解決手段が入っていない環境で「見つからない」と言えていなかった

selftest が捕まえた実バグ。`avahi-resolve` が無いホストで
`Sub.run` が `cannot run avahi-resolve` を投げ、**「Tab5 が見つからない、
こう探せ」の案内に到達しないまま落ちていた**。解決手段ごとに握って
「not installed」として次へ進み、全部だめなときに案内を出す形に直した。
WSL では powershell → getent → avahi の順に試す。

### 5. `/app` は直接 HTTP、画面・入力・ファイルは CLI 委譲

計画の許可どおり `/app/list` `/app/launch` `/app/kill` は lib/tab5.rb から
直接叩き、JSON をそのまま構造化して返す (CLI の表を scrape しない)。
画面 (`fmrb_rd_snap.rb`)、入力 (`fmrb_rd_input.rb`、WebSocket)、
ファイル (`fmrb_rd_fs.rb`、木の走査つき) は CLI へ委譲した — 中身を持ち
込むと薄い層でなくなる。

### 6. 転送のタイムアウトはサイズから見積もる

`put` はファイルサイズ、`push` は木の合計サイズから
`60 秒 + サイズ/10KB/s` で決める (実測 150KB/s に対して十分悲観的)。
`pull` / `rmr` は件数が読めないので定数の倍数。転送系は「大きい転送の間は
remote desktop の配信が止まる (終われば戻る)」を notes に必ず入れる。

### 7. スクリーンショットは image + text の 2 パート

image content (base64 JPEG) に加えて、ファイルパス・バイト数・
フレームサイズを text で返す (`fmrb_pngdiff.rb` 等の後工程用)。
text 側に base64 は入れない。

### 8. P1 と共有部品を切り出した

`Sub.run` / `Sub.scrub` / `Sub.clamp` と `FmrbMcp::Error` を
`lib/support.rb` へ移し、`SerialManager` はそこへ委譲する形にした。
P2 が P1 の子プロセス処理を写経すると、タイムアウトや stdout 汚染の対策が
二重管理になるため。P1 の selftest は変更なしで通る。

## selftest (実機なしで通る、Tab5 分 21 項目 / 合計 53 項目)

偽 Tab5 は rd_http と同じ形の応答を返す最小実装 (`/status` `/app/list`
`/app/launch` `/app/kill` `/fs/list` `/stream` `/ws` と、それ以外は 404)。
**開発エンドポイントの無いリリースビルドを演じるモード**を持つ。

確認しているもの: 住所の検証・キャッシュ・失効と案内文 / image content が
本物の JPEG (FF D8) であること / `/app` の構造化 / **kernel の kill が
説明つきで拒否される** / 未知キーがキー名つきの明示エラーになる /
**404 が「リリースビルド」と診断される** / 引数不足が端末に触る前に落ちる /
9 ツール構成での stdout 純度。

## 実機受け入れ (2026-08-29, Tab5 / 192.168.10.10)

p2_plan.md 5 章。**1-5 は合格**。6 (電源断) はユーザの判断で実施しない。

- **1. IP 解決 — 合格**。`tab5_ip(refresh: true)` が powershell 経由の mDNS で
  `fmruby.local` → `192.168.10.10` を引き、`/status` の `ip` と一致した
  (3.26 秒。以後はキャッシュで即答)。
- **2. 画面 — 合格**。`tab5_screenshot` が 24KB の JPEG を image content で
  返し、426x240 のデスクトップとして読めた (メニューバー・空きメモリ・
  時計まで判別できる)。0.5 秒前後。
- **3. launch → screenshot → kill — 合格**。`/app/demo/kamon.app.rb` を
  パス起動 (pid 5)、`ps` に `Kamon` が現れ、画面にも窓が出て、kill で消えた。
  ランチャーの操作は一切していない。
- **4. put → launch (再 flash なしの開発ループ) — 合格**。その場で書いた
  probe アプリ (.app.rb + .app.toml) を `/app/test/` へ put し、launch し、
  画面に "MCP PROBE OK" が出るところまで確認。後始末は del 2 本
  (`/app/test` はもとからユーザのファイルがある場所なので消していない)。
- **5. 入力 — 合格**。Kamon の「花」ボタンを `click 240 68` で押し、
  ボタンが選択色に変わり紋が花に変わることを次の screenshot で確認。
- 6 (電源断 → 失効 → 再解決失敗の案内) は未実施。selftest では偽 Tab5 を
  止めて同じ経路を通してあり、キャッシュ破棄・案内文・ハングしないことは
  確認済み (実機での再確認だけが残る)。

実機で計画との食い違いは出なかった。tab5_ip の解決に約 3 秒かかるのは
powershell.exe の起動ぶんで、キャッシュが効く 2 回目以降は 0.1 秒以下。
