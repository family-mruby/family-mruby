## 計画との差分 (実装して分かったこと)

### 1. flock は共有部品にした

計画は「P1 の flock を名前 "sim" で再利用」。P1 の実装は SerialManager の
private メソッドだったので、`FmrbMcp::Lock` として support.rb へ切り出し、
両者がそれを使う形にした。`hold(name) { ... }` のブロック形を足してあり、
sim はこちらを使う (シリアルと違い、稼働中ずっと握る必要がない)。
エラー文の「どうすればよいか」は資源ごとに違うので `hint:` で渡す。

### 2. ELF 検査は `file` を呼ばずヘッダを読む

計画は「`file` コマンドでよい」。実際にはヘッダ直読みの方が短く、外部
コマンドに依存せず、**何のビルドかを名指しできる**: RISC-V なら
「ESP32-P4 のビルド」、Xtensa なら「ESP32-S3 のビルド」と返す。
偽の ELF ヘッダを書くだけでテストできるのも利点で、selftest はこれで
偽グリーン遮断を docker 無しに確認している。

### 3. 解像度は PNG から読む (スクリプトの出力を信じない)

`dev_run_check.sh` の stdout には `out.png: WxH` が出るが、これを scrape
せず **PNG の IHDR を読む**。判定の根拠が「実際に撮れた画像」になり、
出力書式が変わっても壊れない。

### 4. `started_by_us` は一度真なら真のまま

計画には無い分岐。自分で起動したスタックに対して 2 回目の `sim_up` を
呼ぶと「稼働中なので再利用」になるが、そこで `started_by_us: false` に
上書きすると、**自分で起動したスタックを自分で down できなくなる**。
過去に真だったら真を保つようにした。

### 5. `sim_app` は debugd の JSON をそのまま返す

`ps` は pid/name/state だけでなく `vm` / `mem_used` / `mem_total` /
`stack_hw` / `exc_hw` / `catch_hw` を返す。要約せずそのまま構造化して
返している (実機の `tab5_app ps` より情報が多い)。

### 6. selftest は「偽のリポジトリ」を使う

P2 の偽 Tab5 に相当するものとして、**argv を印字する偽 CLI と偽 ELF を
置いた一時ディレクトリを repo_root として** Sim を作る。これで docker
なしに、`text "hello world"` が 1 引数のまま渡ること、debugd への
`path=` / `pid=` の渡し方、down 拒否、解像度の期待値を確認できる。
ELF パスは `FMRB_MCP_SIM_CORE_ELF` / `FMRB_MCP_SIM_GA_ELF` で差し替え
られる (計画の提案どおり)。

## selftest (docker なしで通る、sim 分 21 項目 / 合計 73 項目)

偽グリーン遮断 (欠落 / 非 ELF / RISC-V / Xtensa)、引用の生存、debugd への
引数、`started_by_us: false` の down 拒否、Modern/Retro の期待解像度、
PNG からのサイズ読み取り、14 ツールの登録、stdout 純度。

## 受け入れ (2026-08-29、docker + Linux ビルドで自走。全 7 項目合格)

1. **起動 — 合格**。`sim_up` が 17.3 秒で上がり、426x240 (=.env の TAB5) で
   一致。ブート直後の画面 (Family mruby のスプラッシュ) が image で返る。
2. **偽グリーン遮断 — 合格**。実物の `build/fmruby-core.elf` を RISC-V の
   ダミーに差し替えて `sim_up` → **0.0 秒で拒否** (docker に触れない)。
   「RISC-V (an ESP32-P4 build)」と名指し、`rake clean_all && rake
   build:linux` を案内。終わって元に戻した。
3. **解像度の自己修復 — 合格**。`display_conf_linux.txt` を 320x240 に
   書き換えて偽の持ち越しを作り (計画が許した代替手段)、`sim_up` →
   1 回目 320x240 → 自動で down/up → 2 回目 426x240。95 秒。notes に経緯が
   残る。graphics-audio がファイルを 426 に書き戻すので、後始末は不要
   だった (バックアップと一致することを確認済み)。
4. **アプリ — 合格**。`spawn /app/demo/kamon.app.rb` → `ps` に出る →
   画面に窓が見える → `kill`。ランチャー操作なし。
5. **入力 — 合格**。Kamon の「花」を `click 240 68` で押して紋が変わる
   ことを確認。さらにメニュー → Editor を開き、
   `text "puts 12 * 12"` が**空白ごと** 1 行として入る (Ln 1, Col 13) のを
   確認した。ここが P3 で Shellwords を入れた理由そのもの。
6. **ユーザ保護 — 合格**。手で `docker compose up -d` したスタックに対し
   `sim_up` は「再利用した」と報告し (`started_by_us: false`)、
   `sim_down` は force なしで拒否した。
7. **片付け — 合格**。`sim_down(force: true)` でコンテナが残らないことを
   確認 (`docker ps` に fmruby_* なし)。

計測: 冷起動 17.3 秒 / 再利用 3.2 秒 / 自己修復 95 秒 / 偽グリーン拒否 0.0 秒。

## ビルドの状態 (次のセッションへ)

受け入れのため **fmruby-core/build は Linux ビルドに入れ替えた**
(P1 の実機作業のあとは esp32/P4 が入っていた)。fmruby-graphics-audio は
もとから Linux ビルドで、触っていない。`.env` の `FMRB_HW_TARGET=TAB5` は
変えていない。実機に焼くときは `rake clean_all && rake build:esp32` から。
